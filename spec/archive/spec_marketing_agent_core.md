# Спецификация ядра маркетингового агента

**Площадка-модель:** Яндекс Директ (поиск, ручные ставки) · **Реализация:** мок-симулятор + Python · **Цель:** целевой CPA
**Статус:** спецификация ядра (фаза 1). Боевой API, другие площадки и LLM-генерация — вне ядра, см. §13.

---

## 0. Назначение и границы

Агент сам ведёт рекламные сущности как толковый маркетолог: читает метрики, считает KPI с учётом значимости, подкручивает ставки и перераспределяет бюджет, отсекает убыточное и масштабирует прибыльное — и **учится по метрикам**, а не по жёстким порогам.

**Входит в ядро:** канонная модель данных, KPI-движок со статистикой, мок-симулятор аукциона Директа, интерфейс адаптера площадки, ядро оптимизации (гейт + контроллер ставок + bandit-аллокация бюджета + отсечение/масштабирование), guardrails, цикл-оркестратор, память/обучение, объяснимость, критерии приёмки.

**Не входит (фаза 2+, §13):** боевой коннектор Директа, Google/Meta/Telegram, LLM-генерация текстов и ключей, серверная атрибуция/постбэки.

## 1. Сущности и термины

Иерархия (как в Директе): `Account → Campaign → AdGroup → Keyword`.
**Arm (рычаг оптимизации)** — единица, по которой агент принимает решения. По умолчанию arm = **Keyword** (можно поднять до AdGroup через конфиг `OPT_LEVEL`).

Над каждым armом агент управляет двумя рычагами: **ставка (max CPC)** и **дневной бюджетный лимит**. Статус arm'а: `ACTIVE | PAUSED | EXPLORING`.

---

## 2. Канонная модель данных

Платформо-независимая. Адаптер обязан приводить сырьё площадки к этим структурам.

```
EntityRef   { level: "keyword"|"adgroup"|"campaign", id, parent_id }
MetricSnapshot {
  ref: EntityRef, tick, window,
  impressions, clicks, spend, conversions, revenue   # сырые счётчики
}
ArmState {
  ref, status, bid, daily_budget,
  cum_clicks, cum_conv, cum_spend, cum_rev,           # накопленные (для апостериорных)
  CR_hat, CPC_hat, CPA_est, CR_lo, CR_hi              # производные (см. §3)
}
DecisionRecord {                                       # память, §9
  tick, ref, action, before, after, reason, kpis_snapshot
}
```

Единицы: деньги — ₽; ставка/CPC/CPA — ₽; `tick` = один цикл = «день» в моке.

---

## 3. KPI-движок (формулы + значимость)

Сырые KPI:

```
CTR = clicks / impressions
CPC = spend / clicks
CPM = spend / impressions * 1000
CR  = conversions / clicks
CPA = spend / conversions
ROAS = revenue / spend
ROMI = (revenue - spend) / spend
```

**Сглаженная CR (для устойчивости при малых n)** — апостериорное среднее Beta:
```
CR_hat = (cum_conv + α0) / (cum_clicks + α0 + β0)     # prior Beta(α0,β0), дефолт (1,1)
```

**Доверительный интервал CR — Wilson** (нижняя/верхняя границы `CR_lo`, `CR_hi`, уровень `Z=1.96`).
Используется для уверенных действий (пауза/масштабирование):
```
CPA_lo = CPC_hat / CR_hi      # лучший случай (нижняя оценка CPA)
CPA_hi = CPC_hat / CR_lo      # худший случай (верхняя оценка CPA)
CPA_est = CPC_hat / CR_hat    # точечная оценка для контроллера ставок
```

Окно: накопительное по умолчанию; опц. скользящее `WINDOW` тиков (для адаптивности к дрейфу).
Аккаунт-уровень: скользящий `CPA_acct` за `KILL_WINDOW` тиков (для kill-switch, §7).

## 4. Интерфейс адаптера площадки (Platform Adapter)

Ключ к «любой площадке». Ядро работает только через этот контракт. В ядре — реализация `MockYandexDirect`; боевой Директ/иные — позже, тот же контракт.

```
get_metrics(refs, tick) -> [MetricSnapshot]        # статистика за тик
get_state(refs)         -> [ArmState]              # текущие ставки/бюджеты/статусы
set_bid(ref, bid)       -> ok                       # ₽, в пределах площадки
set_budget(ref, daily)  -> ok
set_status(ref, status) -> ok                       # ACTIVE/PAUSED
# create_ad(...), create_keyword(...) — стабы, фаза 2
```

Контракты: идемпотентность `set_*`; значения в ₽; ошибки — типизированные; rate-limit отражает лимиты реального API (§7).

## 5. Мок-симулятор Яндекс Директа (поиск)

Источник «правды» для ядра. Детерминирован (глобальный `SEED`; RNG тика = f(SEED, tick)).

**Скрытые параметры arm'а** (агент их НЕ знает, должен вывести из наблюдений):
```
base_demand        # доступных показов/день при полной видимости
true_ctr           # истинный CTR
true_cr            # истинная конверсия клика
value_per_conv     # ценность конверсии, ₽ (для ROAS)
bid_ref, k         # параметры кривой выкупа (конкуренция)
```

**Модель аукциона (на тик):**
```
IS(bid)   = bid^k / (bid^k + bid_ref^k)             # доля показов, убывающая отдача (Hill)
dow       = seasonality[tick % 7]                    # недельная сезонность
impressions = round(base_demand * IS(bid) * dow * noise_imp)
clicks      ~ Binomial(impressions, true_ctr * pos_uplift(bid))
cpc         = bid * cpc_ratio(bid)                   # ratio∈(0.6..0.95), растёт с bid (≈второй цене)
spend       = min(clicks * cpc, daily_budget)        # при исчерпании бюджета показы стопаются
conversions ~ Binomial(clicks_paid, true_cr)
revenue     = conversions * value_per_conv
```

Шум: мультипликативный лог-нормальный (`noise_imp`, на cpc). Опц. флаг `DRIFT`: `true_cr` медленно смещается с середины прогона — тест адаптивности.

**Зачем так:** `cpc` растёт с `bid` (убывающая отдача), `CR` — свойство arm'а, почти не зависит от ставки. Значит `CPA = cpc/CR` управляемо через ставку — на этом стоит контроллер §6.2. Наличие «оракула» (истинных параметров) позволяет в приёмке сравнить агента с теоретическим оптимумом.

## 6. Ядро оптимизации

Слои применяются в фиксированном порядке (см. цикл §8). Конфликты разрешаются приоритетом: пауза > ставка > бюджет > масштаб.

### 6.1. Статистический гейт
Жёсткие действия — только при достаточных данных:
- менять ставку: `cum_clicks ≥ N_MIN_BID` (дефолт 30), иначе ставка держится на `BID_DEFAULT`;
- ставить паузу: `cum_clicks ≥ N_MIN_PAUSE` (100);
- масштабировать: `cum_clicks ≥ N_MIN_SCALE` (100).
Недоисследованные армы (ниже порога) получают статус `EXPLORING` и долю explore-бюджета (§6.3).

### 6.2. Контроллер ставок → целевой CPA
Демпфированная пропорциональная подстройка:
```
ratio  = clamp(TARGET_CPA / CPA_est, 0.5, 2.0)
factor = clamp(ratio^γ, 1 - MAX_STEP, 1 + MAX_STEP)        # γ=0.5, MAX_STEP=0.20
new_bid = clamp(old_bid * factor, BID_FLOOR, BID_CEIL)
```
`CPA_est > TARGET` → `factor<1` → ставка вниз (дешевле трафик); `<TARGET` → вверх (объём). `γ<1` гасит раскачку.

### 6.3. Bandit-аллокация дневного бюджета (Thompson sampling)
Общий дневной бюджет `B` (конфиг). Делится:
- **Explore-резерв** `EXPLORE_FRAC` (дефолт 0.15) — поровну между `EXPLORING`-армами (дать им шанс набрать данные).
- **Exploit** `(1 - EXPLORE_FRAC)` — между `ACTIVE`-армами пропорционально сэмплированной эффективности:
```
CR_sample_i  ~ Beta(cum_conv_i + α0, cum_clicks_i - cum_conv_i + β0)
eff_i        = CR_sample_i / CPC_hat_i          # конверсий на ₽ (=1/CPA); для ROAS ×value_i
budget_i     = B*(1-EXPLORE_FRAC) * eff_i / Σ eff
```
Сэмплирование Beta даёт исследование автоматически: неуверенные армы иногда получают высокий сэмпл и тестируются. Это и есть «самообучение по метрикам».

### 6.4. Отсечение (пауза) и масштабирование
**Пауза** arm'а, если уверенно дорог: `cum_clicks ≥ N_MIN_PAUSE` И `CPA_lo > TARGET_CPA * PAUSE_FACTOR` (1.5) — даже лучший случай хуже цели.
**Масштаб**, если уверенно прибылен И упирается в лимит: `cum_clicks ≥ N_MIN_SCALE` И `CPA_hi < TARGET_CPA * SCALE_FACTOR` (0.8) И `spend ≥ SCALE_SPEND_FRAC * daily_budget` → поднять лимит на `SCALE_UP` (+30%), в пределах `B`.

## 7. Guardrails (жёсткие инварианты — не нарушаются никогда)

1. Шаг ставки за тик ≤ `MAX_STEP` (20%); `bid ∈ [BID_FLOOR, BID_CEIL]`.
2. Суммарный дневной расход ≤ `B_MAX` (жёсткий потолок).
3. Нет паузы без `N_MIN_PAUSE` кликов и пройденной значимости.
4. ≤ `MAX_CHANGES_PER_TICK` изменений за тик (имитация лимитов API).
5. Каждое действие логируется (before/after + причина) и обратимо.
6. **Kill-switch:** если `CPA_acct` за `KILL_WINDOW` > `CATASTROPHE_CPA` → остановить откат изменений, заморозить, алерт человеку (human-in-the-loop).

## 8. Цикл-оркестратор (один tick)

```
1. metrics = adapter.get_metrics(refs, tick); update store, накопленные счётчики
2. recompute KPI: CR_hat, CPC_hat, CPA_est, CR_lo/hi, CPA_lo/hi, CPA_acct
3. kill-switch (§7.6) — при срабатывании halt
4. PRUNE: пауза подтверждённым лузерам (§6.4)
5. BID: контроллер ставок по гейту (§6.1–6.2)
6. BUDGET: bandit-аллокация (explore + exploit) (§6.3)
7. SCALE: поднять лимиты подтверждённым победителям (§6.4)
8. EXECUTOR: применить через адаптер под guardrails (clamp, rate-limit, лог)
9. записать DecisionRecord'ы в память (§9)
10. tick += 1
```

---

## 9. Память и обучение

Хранится на каждый тик: метрики arm'а, действие, причина, KPI-срез; и аккаунт-уровень (скользящие KPI).
Используется для: (а) апостериорных распределений (накопленные conv/clicks → bandit и Wilson), (б) обнаружения дрейфа/тренда, (в) графиков приёмки, (г) объяснимости.
Обучение = накопление статистики сдвигает апостериорные → аллокация и ставки сходятся к выгодным armам. Никакого оффлайн-обучения модели не требуется.

## 10. Объяснимость

Каждое решение — человеко-читаемая строка причины. Формат:
```
[tick 23] keyword "учить английский онлайн": ставка 14.0→11.8 ₽
  причина: CPA_est=210₽ > target=150₽; снижаю ставку (factor 0.84)
[tick 23] keyword "english b1": ПАУЗА
  причина: CPA_lo=320₽ > target*1.5=225₽ при 140 кликах — уверенно дорог
```
Это закрывает требование «ведёт как толковый маркетолог»: видно не только *что*, но и *почему*.

## 12. Критерии приёмки (демо-сценарий)

Прогон `M` тиков (дефолт 60). Агент сравнивается с двумя бейзлайнами.

| Проверка | Ожидание |
|---|---|
| Сходимость | скользящий `CPA_acct` снижается и стабилизируется ≤ `TARGET_CPA` |
| Объём | конверсий/тик растёт по ходу прогона |
| vs baseline | агент бьёт «равный бюджет + фикс. ставка» по CPA при не меньшем числе конверсий |
| vs oracle | агент приближается к оптимуму при истинных параметрах |
| Guardrails | ни один тик не превышает `B_MAX`; ни одной паузы до `N_MIN_PAUSE`; шаг ставки ≤ `MAX_STEP` |
| Адаптивность | при `DRIFT=on` агент перебалансируется за ≤ `K` тиков |
| Объяснимость | у каждого решения читаемая причина; пример лога приложен |

Артефакты демо: график `CPA_acct` и конверсий по тикам; таблица «агент vs baseline vs oracle»; сэмпл лога решений.
