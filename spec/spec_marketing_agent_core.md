# Спецификация ядра маркетингового агента

**Ред. 2** — добавлен РСЯ (обе площадки оптимизируются на целевой CPA).
**Площадка-модель:** Яндекс Директ — **поиск (CPC) + РСЯ (CPM)**, ручные ставки · **Реализация:** мок-симулятор + Python · **Цель:** целевой CPA для обоих типов инвентаря.
**Статус:** спецификация ядра (фаза 1). Боевой API, другие площадки и LLM-генерация — вне ядра, см. §13.

---

## 0. Назначение и границы

Агент сам ведёт рекламные сущности как толковый маркетолог: читает метрики, считает KPI с учётом значимости, подкручивает ставки и перераспределяет бюджет, отсекает убыточное и масштабирует прибыльное — и **учится по метрикам**, а не по жёстким порогам. Поиск и РСЯ оптимизируются к одной цели (целевой CPA), различаются только рычагом ставки (CPC vs CPM).

**Входит в ядро:** канонная модель данных, KPI-движок со статистикой, мок-симулятор аукциона Директа (две модели инвентаря), интерфейс адаптера, ядро оптимизации (гейт + контроллер ставок + bandit-аллокация бюджета + отсечение/масштабирование), guardrails, цикл-оркестратор, память/обучение, объяснимость, критерии приёмки.

**Не входит (фаза 2+, §13):** боевой коннектор Директа, Google/Meta/Telegram, LLM-генерация текстов и ключей, серверная атрибуция/постбэки.

## 1. Сущности и термины

Иерархия (как в Директе): `Account → Campaign → AdGroup → (Keyword | Placement)`.

**Arm (рычаг оптимизации)** — единица решения. Зависит от типа инвентаря:

| Тип инвентаря (`inv_type`) | Arm | Ставка (`bid_unit`) | Природа трафика |
|---|---|---|---|
| `search` (поиск) | ключевая фраза | **CPC**, ₽/клик | горячий, высокий CTR/CR |
| `network` (РСЯ) | площадка / аудитория-сегмент | **CPM**, ₽/1000 показов | холоднее, низкий CTR/CR |

По умолчанию `OPT_LEVEL` = arm. Над каждым armом агент управляет двумя рычагами: **ставка** (CPC или CPM) и **дневной бюджетный лимит**. Статус: `ACTIVE | PAUSED | EXPLORING`. Цель для обоих типов — целевой CPA; различается только формула CPA от ставки (§3) и контроллер (§6.2).

## 2. Канонная модель данных

Платформо-независимая. Адаптер приводит сырьё площадки к этим структурам.

```
EntityRef   { level: "keyword"|"placement"|"adgroup"|"campaign", id, parent_id, inv_type: "search"|"network" }
MetricSnapshot {
  ref, tick, window,
  impressions, clicks, spend, conversions, revenue   # сырые счётчики
}
ArmState {
  ref, status, bid, bid_unit: "CPC"|"CPM", daily_budget,
  cum_imp, cum_clicks, cum_conv, cum_spend, cum_rev,  # накопленные (для апостериорных)
  CTR_hat, CR_hat, CPC_hat, CPM_hat, CPA_est,         # производные (§3)
  CTR_lo, CTR_hi, CR_lo, CR_hi, CPA_lo, CPA_hi
}
DecisionRecord { tick, ref, action, before, after, reason, kpis_snapshot }   # память, §9
```

Единицы: деньги — ₽; CPC/CPA — ₽; CPM — ₽/1000 показов; `tick` = один цикл = «день».

## 3. KPI-движок (формулы + значимость)

Сырые KPI:
```
CTR = clicks / impressions
CPC = spend / clicks
CPM = spend / impressions * 1000
CR  = conversions / clicks
CPA = spend / conversions
ROAS = revenue / spend ;  ROMI = (revenue - spend) / spend
```

**Сглаженные оценки (Beta, для устойчивости при малых n):**
```
CR_hat  = (cum_conv  + α0)    / (cum_clicks + α0 + β0)        # prior Beta(α0,β0), дефолт (1,1)
CTR_hat = (cum_clicks + αc)   / (cum_imp + αc + βc)           # для network; prior (1,1)
CPC_hat = cum_spend / cum_clicks ;  CPM_hat = cum_spend / cum_imp * 1000
```

**Доверительные интервалы — Wilson** (Z=1.96) на CR (по кликам) и CTR (по показам) → `CR_lo/hi`, `CTR_lo/hi`.

**CPA — главный показатель оптимизации. Формула зависит от типа:**
```
search :  CPA_est = CPC_hat / CR_hat
network:  CPA_est = CPM_hat / (1000 * CTR_hat * CR_hat)
```
Эффективность (конверсий на ₽, для bandit §6.3):
```
search :  eff = CR_hat / CPC_hat
network:  eff = 1000 * CTR_hat * CR_hat / CPM_hat
```
Границы CPA (для уверенных действий §6.4):
```
search :  CPA_lo = CPC_hat / CR_hi ;            CPA_hi = CPC_hat / CR_lo
network:  CPA_lo = CPM_hat / (1000*CTR_hi*CR_hi); CPA_hi = CPM_hat / (1000*CTR_lo*CR_lo)
```
`CPA_lo` = лучший случай, `CPA_hi` = худший. Окно: накопительное (дефолт) или скользящее `WINDOW` тиков. Аккаунт-уровень: скользящий `CPA_acct` за `KILL_WINDOW` тиков (kill-switch §7).

## 4. Интерфейс адаптера площадки (Platform Adapter)

Ключ к «любой площадке». Ядро работает только через контракт. В ядре — `MockYandexDirect` (обе модели инвентаря); боевой Директ/иные — позже, тот же контракт.

```
get_metrics(refs, tick) -> [MetricSnapshot]
get_state(refs)         -> [ArmState]
set_bid(ref, bid)       -> ok      # значение в bid_unit арма (CPC или CPM), ₽
set_budget(ref, daily)  -> ok
set_status(ref, status) -> ok      # ACTIVE/PAUSED
# create_ad / create_keyword / create_placement — стабы, фаза 2
```
Контракты: идемпотентность `set_*`; типизированные ошибки; rate-limit отражает лимиты реального API (§7).

## 5. Мок-симулятор Яндекс Директа (две модели инвентаря)

Источник «правды». Детерминирован (`SEED`; RNG тика = f(SEED, tick)). Недельная сезонность `seasonality[7]`, мультипликативный лог-нормальный шум. Опц. флаг `DRIFT`: истинная конверсия медленно смещается с середины прогона — тест адаптивности.

**Скрытые параметры arm'а (агент не знает):**
`search`: `base_demand, true_ctr, true_cr, value_per_conv, bid_ref, k`
`network`: `base_demand_imp, true_ctr_net (≪ поиска), true_cr_net (< поиска), value_per_conv, cpm_ref, k`

**Аукцион — поиск (CPC):**
```
IS(bid)     = bid^k / (bid^k + bid_ref^k)            # доля показов, убывающая отдача
impressions = base_demand * IS(bid) * dow * noise
cpc         = bid * cpc_ratio(bid)                   # ratio∈(0.6..0.95), растёт с bid (≈второй цене)
clicks      ~ Binomial(impressions, true_ctr * pos_uplift(bid))
spend       = min(clicks * cpc, daily_budget)        # при исчерпании — показы стоп
conversions ~ Binomial(clicks_paid, true_cr) ; revenue = conversions * value_per_conv
```

**Аукцион — РСЯ (CPM):**
```
IS(cpm)     = cpm^k / (cpm^k + cpm_ref^k)
impressions = base_demand_imp * IS(cpm) * dow * noise * freq_sat   # freq_sat≤1, опц. насыщение частоты
cpm_real    = cpm * cpm_ratio(cpm)                   # ratio∈(0.6..0.95)
spend       = min(impressions * cpm_real / 1000, daily_budget)
clicks      ~ Binomial(impressions, true_ctr_net)
conversions ~ Binomial(clicks, true_cr_net) ; revenue = conversions * value_per_conv
```

**Зачем так:** ставка управляет ценой и объёмом (убывающая отдача), а CTR/CR — свойства арма. Значит `CPA` управляем через ставку — на этом стоит контроллер §6.2. «Оракул» (истинные параметры) позволяет в приёмке сравнить агента с оптимумом.
*Caveat:* на боевом Директе ручное управление ставками в РСЯ ограничено — там «target CPA» агента маппится на параметры CPA-автостратегии, а не на сырой CPM (см. §13). В моке управляем CPM напрямую — это корректная учебная модель того же закона «ставка → цена/объём».

## 6. Ядро оптимизации

Слои применяются в фиксированном порядке (цикл §8). Приоритет конфликтов: пауза > ставка > бюджет > масштаб. Логика **единая для обоих типов**; различается только формула CPA/eff и единица ставки.

### 6.1. Статистический гейт
- менять ставку: `cum_clicks ≥ N_MIN_BID` (30); для `network` дополнительно `cum_imp ≥ N_MIN_IMP` (3000) — иначе CTR недостоверен;
- ставить паузу: `cum_clicks ≥ N_MIN_PAUSE` (100) [+ `cum_imp ≥ N_MIN_IMP` для network];
- масштабировать: те же пороги, что для паузы.
Недоисследованные армы → статус `EXPLORING` + доля explore-бюджета (§6.3).

### 6.2. Контроллер ставок → целевой CPA
Демпфированная пропорциональная подстройка (одна формула, рычаг = `bid_unit`):
```
ratio   = clamp(TARGET_CPA / CPA_est, 0.5, 2.0)
factor  = clamp(ratio^γ, 1 - MAX_STEP, 1 + MAX_STEP)         # γ=0.5, MAX_STEP=0.20
new_bid = clamp(old_bid * factor, BID_FLOOR[inv], BID_CEIL[inv])
```
`CPA_est > TARGET` → `factor<1` → ставка вниз; `<TARGET` → вверх. Для `search` рычаг — CPC, для `network` — CPM; границы `BID_FLOOR/CEIL` свои на тип.

### 6.3. Bandit-аллокация дневного бюджета (Thompson sampling, единый пул)
Все `ACTIVE`-армы (поиск + РСЯ) конкурируют за общий бюджет `B`:
- **Explore-резерв** `EXPLORE_FRAC` (0.15) — поровну между `EXPLORING`-армами.
- **Exploit** `(1-EXPLORE_FRAC)` — пропорционально сэмплированной эффективности:
```
CR_s  ~ Beta(cum_conv + α0, cum_clicks - cum_conv + β0)
search :  eff_s = CR_s / CPC_hat
network:  CTR_s ~ Beta(cum_clicks + αc, cum_imp - cum_clicks + βc)
          eff_s = 1000 * CTR_s * CR_s / CPM_hat
budget_i = B*(1-EXPLORE_FRAC) * eff_s_i / Σ eff_s
```
Сэмплирование Beta даёт исследование автоматически — это и есть «самообучение по метрикам». Единый пул честно сравнивает поиск и РСЯ по конверсиям на ₽.

### 6.4. Отсечение (пауза) и масштабирование
**Пауза**, если уверенно дорог: гейт пройден И `CPA_lo > TARGET_CPA * PAUSE_FACTOR` (1.5) — даже лучший случай хуже цели.
**Масштаб**, если уверенно прибылен И упирается в лимит: гейт пройден И `CPA_hi < TARGET_CPA * SCALE_FACTOR` (0.8) И `spend ≥ SCALE_SPEND_FRAC * daily_budget` → поднять лимит на `SCALE_UP` (+30%), в пределах `B`.

## 7. Guardrails (жёсткие инварианты)

1. Шаг ставки за тик ≤ `MAX_STEP` (20%); `bid ∈ [BID_FLOOR[inv], BID_CEIL[inv]]` (свои для CPC и CPM).
2. Суммарный дневной расход ≤ `B_MAX` (жёсткий потолок).
3. Нет паузы без пройденного гейта значимости (§6.1).
4. ≤ `MAX_CHANGES_PER_TICK` изменений за тик (имитация лимитов API).
5. Каждое действие логируется (before/after + причина) и обратимо.
6. **Kill-switch:** `CPA_acct` за `KILL_WINDOW` > `CATASTROPHE_CPA` → заморозить изменения, алерт человеку (human-in-the-loop).
7. (Опц.) частотный потолок для `network` — ограничение показов на аудиторию.

## 8. Цикл-оркестратор (один tick)

```
1. metrics = adapter.get_metrics(refs, tick); update store, накопленные счётчики
2. recompute KPI: CTR_hat, CR_hat, CPC/CPM_hat, CPA_est, *_lo/hi, CPA_acct
3. kill-switch (§7.6) — при срабатывании halt
4. PRUNE: пауза подтверждённым лузерам (§6.4)
5. BID: контроллер ставок по гейту (§6.1–6.2), рычаг по типу инвентаря
6. BUDGET: bandit-аллокация единым пулом (explore + exploit) (§6.3)
7. SCALE: поднять лимиты подтверждённым победителям (§6.4)
8. EXECUTOR: применить через адаптер под guardrails (clamp, rate-limit, лог)
9. записать DecisionRecord'ы в память (§9)
10. tick += 1
```

## 9. Память и обучение

Хранится на тик: метрики арма, действие, причина, KPI-срез; аккаунт-уровень (скользящие KPI).
Используется для: (а) апостериорных (накопл. imp/clicks/conv → bandit, Wilson), (б) обнаружения дрейфа/тренда, (в) графиков приёмки, (г) объяснимости.
Обучение = накопление статистики сдвигает апостериорные → аллокация и ставки сходятся к выгодным armам. Оффлайн-обучение модели не требуется.

## 10. Объяснимость

Каждое решение — человеко-читаемая причина:
```
[tick 23] search "учить английский онлайн": CPC 14.0→11.8 ₽
  причина: CPA_est=210₽ > target=150₽; снижаю ставку (factor 0.84)
[tick 23] network "канал @eng_blog": ПАУЗА
  причина: CPA_lo=340₽ > target*1.5=225₽ при 5200 показах / 90 кликах — уверенно дорог
```
Закрывает требование «ведёт как толковый маркетолог»: видно не только *что*, но и *почему*.

## 12. Критерии приёмки (демо-сценарий)

Прогон `M` тиков (60). Агент сравнивается с бейзлайнами; смесь поиск+РСЯ в стартовом наборе armов.

| Проверка | Ожидание |
|---|---|
| Сходимость | скользящий `CPA_acct` снижается и стабилизируется ≤ `TARGET_CPA` |
| Объём | конверсий/тик растёт по ходу прогона |
| Микс | бюджет перетекает к более эффективному типу (поиск/РСЯ) по конверсиям на ₽ |
| vs baseline | агент бьёт «равный бюджет + фикс. ставка» по CPA при не меньшем числе конверсий |
| vs oracle | агент приближается к оптимуму при истинных параметрах |
| Guardrails | ни один тик не превышает `B_MAX`; нет пауз до гейта; шаг ставки ≤ `MAX_STEP` |
| Адаптивность | при `DRIFT=on` перебалансировка за ≤ `K` тиков |
| Объяснимость | у каждого решения читаемая причина; пример лога приложен |

Артефакты демо: график `CPA_acct` и конверсий по тикам; разбивка бюджета поиск/РСЯ; таблица «агент vs baseline vs oracle»; сэмпл лога решений.

## 13. Границы и next step

- **Боевой Директ:** заменить `MockYandexDirect` на коннектор (OAuth; Campaigns/KeywordBids/Strategies — управление; Reports — статистика; есть тестовая среда). Контракт §4 не меняется. Для РСЯ «target CPA» агента маппится на параметры CPA-автостратегии Директа (ручной CPM на боевом ограничен), для поиска — на ручные CPC-ставки.
- **Другие площадки:** новая реализация адаптера; ядро §6–§8 переиспользуется.
- **LLM-слой (фаза 2):** генерация/итерация текстов, ключей и подбор площадок; трактовка аномалий; формулировка стратегии. LLM = стратег, математика §6 = оптимизатор.
- **Атрибуция:** серверные постбэки/конверсии из продукта (для ИП Изи Пизи: установка / старт триала / подписчик → CPI / cost-per-trial / CAC vs LTV).
